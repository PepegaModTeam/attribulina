# NFS-VltEd 4.6's names for the parts of Undercover (PC) values: the words nfsms
# scripts write after the field (update_field car_tuning x TORQUE MinY 90).
# doc/nfsms.md. Written by scripts/nfsms/gen_words.py; rerun it rather than editing
# by hand.
#
# Read from the NFS-VltEd decompilation (NFS-VltEd/). A/_0007_0014.cs registers one
# C# class per AttribSys type and game, keyed by StringHash32 of the type name; each
# class names its properties with an attribute and reads them in order, which gives
# each name its offset in the PC files NFS-VltEd reads. The path after the offset
# names the member of Undercover's PC types (below) at those bytes, so a word finds
# its member by name on a platform whose layout differs (4-byte bools move later
# members). An Undercover type not listed here gets NFS-VltEd's raw class: its one
# property is Data, the value's bytes in hex ("00 00 80 3F").
#
# NFS-VltEd's Undercover is the PC game, the current-generation one (PC, 360). Its
# Wii and PS2 versions are another game on Carbon's engine with mostly other types
# (the "# not on wii" comments). This script lays the PC's types out from
# nfs-data/SpeedDebugOpt-enUS.h (the 360 debug build, member order only) at the PC's
# alignment, checked against the PC type table's sizes, as
# data/schema/undercover_pc.txt does, and the paths name those members.
#
# game <code>
# type <AttribSys type name>      Attrib::StringKey(MODEL): a StringKey field named MODEL
#   single                        one property: NFS-VltEd ignores the word after the field
#   <word> <offset> :<type> [<path>] [list <element words>]
# end
#
# <path>: member names joined with ".", [i] for an element of an inline array, down
# to the member the word sets (Reaction.mClassKey, ValueMin[1]). A word over several
# members has the deepest member holding them all (X for X.mArray and X.mLength). A
# path ending in +N: the word's bytes start N bytes into that member. No path: the
# word's members have nothing in common but the value itself, or the type has no
# struct in our schema (enums, vectors, simple values), where the offset is the same
# on every platform.
#
# <type>: what NFS-VltEd itself reads and writes at the offset, which its NFS-VltEd
# compatible reading uses (doc/nfsms.md): u8, i8, u16, i16, u32, i32, u64, i64, f32,
# f64, bool8 (a byte, 1 is true), bool32; then /key (a name, hashed with
# StringHash32; 0x and 8 hex digits is the number), /binkey (a decimal number is
# itself, else bStringHash), /key64, /hex (0x hex or decimal) or /hexdigits (hex
# digits, 0x or not). i32>f32: the file holds an i32 that NFS-VltEd shows as a
# float. A list word has the list's kind (f32list, keylist, refspeclist, ...),
# string a char* and blob a size and pointer.
#
# The comments give where each class was read and how sure the game assignment is:
# "read" means registered for Undercover or for every game, or in a compiled array
# whose bytes other code shows; "inferred" and "uncertain" mean the game list is a
# compiled array the decompilation lacks, so it was worked out (see the comment and
# scripts/nfsms/registry.py). After a word, "# x" lists our schema's members at its
# bytes where the path doesn't name them all. "# not on <platform>" marks a word
# that can't be found that way in that platform's schema, or a type its files lack;
# "# on <platform>" a type laid out otherwise there whose words all find their
# members.
